Überblick

Argo CD vergleicht zwei Zustände: das, was in Git steht (Desired State), und das, was im Cluster läuft (Live State). Wie dieser Vergleich gerechnet wird, legt die Diff-Strategie fest.

Legacy (Client-Side) Diff

Der Application Controller rechnet den Diff selbst, ohne den API-Server zu fragen. Das ist weiterhin der Default.

Server-Side Diff (SSD)

Der Controller schickt das Manifest als Server-Side Apply im Dry-Run an den API-Server und vergleicht das Ergebnis mit dem Live State.

Client-Side schätzt, Server-Side fragt. Legacy ist der Kostenvoranschlag aus dem Gedächtnis, Server-Side Diff die Probefahrt mit dem echten Fahrzeug.
1

Die drei Diff-Strategien

Argo CD kennt drei Strategien. Welche greift, ergibt sich aus zwei Schaltern, die nacheinander geprüft werden.

  1. Legacy3-Way-Merge im Controller. Default.
  2. Structured-Merge DiffWird automatisch genutzt, sobald die Sync-Option ServerSideApply=true aktiv ist und kein Server-Side Diff eingeschaltet ist. Basiert auf der Kubernetes-Bibliothek structured-merge-diff, läuft aber weiterhin lokal im Controller.
  3. Server-Side DiffServer-Side Apply im Dry-Run-Modus gegen den API-Server.

Welche Strategie greift

Structured-Merge Diff wird eingestellt. Die Argo-CD-Doku (Release 3.2) führt die Strategie als „Feature Discontinued“: Nach mehreren Problemen aus der Community wird sie zugunsten von Server-Side Diff aufgegeben. Wer Server-Side Apply nutzt, sollte Server-Side Diff deshalb mit einschalten, statt sich auf den automatischen Fallback zu verlassen.
2

Legacy Diff: 3-Way-Merge im Controller

Beim Legacy-Diff kombiniert der Controller drei Quellen und berechnet daraus lokal, wie das Objekt nach einem Apply aussehen würde. Das Ergebnis vergleicht er mit dem Live State.

Drei Quellen, ein lokaler Merge

Grenzen

  • Defaults: Der API-Server ergänzt Felder wie imagePullPolicy, protocol: TCP oder terminationMessagePath. Für eingebaute Typen kennt Argo CD viele davon, für CRD-Defaults nicht.
  • Listen: Ohne Schema-Wissen werden Listen als Ganzes betrachtet. Ein von einem Controller ergänzter Eintrag oder ein Default innerhalb eines Listenelements erzeugt Drift.
  • Normalisierung: Werte wie cpu: 1000m speichert der Server als cpu: "1". Solche Umschreibungen müssen lokal nachgebildet werden.
  • Admission: Webhooks laufen nur im Cluster. Fehler zeigen sich erst beim Sync.
  • Annotation-Limit: last-applied-configuration unterliegt der Größengrenze für Annotations (256 KiB). Große CRDs scheitern daran.
Übliche Gegenmaßnahme: ignoreDifferences-Einträge und Normalizer im argocd-cm. Sie behandeln Symptome, nicht die Ursache.
3

Server-Side Diff: Dry-Run am API-Server

Der Controller schickt jedes Manifest als Server-Side-Apply-Patch mit dryRun=All an den API-Server. Der Server durchläuft seine normale Verarbeitungskette, schreibt aber nichts nach etcd. Zurück kommt der vorhergesagte Live State, den Argo CD mit dem tatsächlichen Live State vergleicht.

Ablauf eines Dry-Runs

Generalprobe ohne Publikum. Der API-Server spielt das ganze Stück durch – Conversion, Defaults, Validierung, Webhooks –, aber der Vorhang (etcd) bleibt zu.

Caching

Die Ergebnisse werden zwischengespeichert. Ein neuer Dry-Run geht nur raus, wenn

  • ein Refresh oder Hard-Refresh der Application angefordert wird,
  • eine neue Revision im Repo vorliegt, auf das die Application zeigt,
  • sich die Application-Spec geändert hat,
  • sich die resourceVersion der Live-Ressource geändert hat.

Einschränkung: neue Ressourcen

Für Ressourcen, die noch nicht im Cluster existieren, wird kein Server-Side Diff ausgeführt. Argo CD nutzt dann einen einfacheren Diff ohne Dry-Run.

Folge: Validierende Webhooks laufen beim Diff einer noch nicht angelegten Ressource nicht mit. Deren Ablehnung zeigt sich wie bisher erst beim Sync.

4

Diff und Apply: zwei getrennte Schalter

Häufige Verwechslung: Server-Side Diff bestimmt, wie Argo CD vergleicht. Server-Side Apply (Sync-Option, seit 2.5) bestimmt, wie Argo CD schreibt. Beides lässt sich unabhängig schalten.

Diff ist die Brille, Apply der Stift. Mit der Brille sieht man, was abweicht; mit dem Stift wird geschrieben. Beides vom selben Hersteller passt am besten zusammen.

5

Field Ownership mit managedFields

Server-Side Apply ersetzt die last-applied-configuration-Annotation durch metadata.managedFields. Dort ist für jedes Feld eingetragen, welcher Field Manager es besitzt.

metadata:
  managedFields:
    - manager: argocd-controller
      operation: Apply
      apiVersion: apps/v1
      fieldsType: FieldsV1
      fieldsV1:
        f:spec:
          f:template:
            f:spec:
              f:containers:
                k:{"name":"web"}:
                  f:image: {}
                  f:ports: {}
    - manager: kube-controller-manager
      operation: Update
      apiVersion: apps/v1
      fieldsType: FieldsV1
      fieldsV1:
        f:spec:
          f:replicas: {}

Lesehilfe

  • f: steht für ein Feld.
  • k:{"name":"web"} steht für einen Listeneintrag, identifiziert über den Merge-Key name, nicht über die Position. Die Ownership bleibt stabil, wenn sich die Reihenfolge ändert.
  • {} markiert nur den Besitz. Werte stehen nicht in managedFields.
  • operation: Apply bedeutet deklaratives Setzen per Server-Side Apply, operation: Update klassisches PUT/PATCH, typisch für Controller.

Folgen für den Diff

  • Felder, die nicht in Git stehen und einem anderen Manager gehören (im Beispiel spec.replicas des HPA), erscheinen nicht als Drift.
  • Felder, die in Git stehen, werden weiterhin verglichen. Ändert jemand image per kubectl edit, zeigt der Server-Side Diff das als Drift an, weil der Dry-Run-Apply den Wert zurücksetzen würde.
  • Beanspruchen Git und ein Controller dasselbe Feld (z. B. replicas in Git plus HPA), überschreiben sich beide gegenseitig. Lösung: das Feld aus dem Manifest entfernen.
managedFields ist das Grundbuch des Objekts. Für jedes Flurstück (Feld) steht ein Eigentümer drin. Argo CD streitet nur um die Grundstücke, die auf seinen Namen eingetragen sind.
6

Praxisfälle

Vier Situationen, in denen sich Legacy und Server-Side Diff sichtbar unterscheiden.

6.1 CRD-Defaults

Ein CRD-Schema kann Defaults festlegen:

spec:
  type: object
  properties:
    affinity:
      type: object
      properties:
        podAffinityType:
          type: string
          default: "preferred"
    enablePDB:
      type: boolean
      default: true

Fehlen diese Felder in der Custom Resource in Git, ergänzt der API-Server sie. Der Server-Side Diff erhält dieselben Defaults aus dem Dry-Run, also entsteht kein Diff. Der Legacy-Diff kennt das CRD-Schema nicht und kann je nach Situation Fake-Drift melden: bei Defaults in Listenelementen, bei fehlender last-applied-configuration oder bei explizit leeren Werten.

Defaults greifen nur innerhalb existierender Objekte. podAffinityType wird nur gesetzt, wenn spec.affinity in der CR vorhanden ist (oder affinity selbst einen Default {} hat). enablePDB liegt direkt unter spec und wird immer ergänzt.

6.2 CRD-Versionen und Validierung

  • Conversion: Steht in Git eine ältere API-Version (z. B. v1beta1) und ist v1 die Storage-Version, läuft der Dry-Run durch die echte Conversion-Kette des Servers.
  • Validierung: required, enum, pattern und CEL-Regeln (x-kubernetes-validations) greifen bereits beim Diff.
  • Listen-Semantik: x-kubernetes-list-type: map und x-kubernetes-list-map-keys sagen dem Server, dass eine Liste über einen Schlüssel gemergt wird. Das verhindert Drift durch geänderte Reihenfolge oder ergänzte Einträge.

6.3 Admission Webhooks: Fehler vor dem Sync

Beispiel: Eine Gatekeeper-Constraint begrenzt CPU-Requests auf maximal 2. In Git wird versehentlich cpu: 5 eingetragen.

Ohne Server-Side Diff

Argo CD zeigt nur OutOfSync. Erst beim Sync lehnt der Webhook den Apply ab, die Operation endet mit Phase Failed. Andere Ressourcen derselben Sync-Wave können zu diesem Zeitpunkt bereits angewendet sein.

Mit Server-Side Diff

Schon der Dry-Run läuft durch die Admission-Kette. Die Application zeigt direkt nach dem Commit einen ComparisonError mit der Ablehnungsmeldung des Webhooks. Ein Sync wird gar nicht erst versucht.

Nebenwirkung: Ein ComparisonError betrifft die ganze Application. Bis der Fehler behoben ist, fehlt die Diff-Anzeige auch für die übrigen Ressourcen.

6.4 Mutating Webhooks

Mutierende Webhooks (z. B. Istio-Sidecar-Injection, Kyverno-Mutationen) werden beim Server-Side Diff standardmäßig nicht einbezogen. Sollen ihre Änderungen in den Diff einfließen, braucht die Application zusätzlich IncludeMutationWebhook=true (siehe Abschnitt 8). Die Option wirkt nur bei aktivem Server-Side Diff.

7

Vor- und Nachteile

Weniger Fake-Drift und frühere Fehler gegen zusätzliche Last am API-Server und ein paar Sonderfälle.

Vorteile

  • Deutlich weniger Fake-Drift durch Defaults, Normalisierung und CRD-Schemas.
  • Weniger ignoreDifferences-Einträge nötig.
  • Policy-Verstöße (Gatekeeper, Kyverno, CEL) fallen beim Vergleich auf, nicht erst beim Sync.
  • In Kombination mit Server-Side Apply: Field Ownership statt Annotation, saubere Koexistenz mit HPA, VPA und Operatoren, korrekte Entfernung gelöschter Felder, keine 256-KiB-Grenze.

Nachteile und Einschränkungen

  • Zusätzliche Last auf dem API-Server: ein Dry-Run je Ressource, abgefedert durch Caching.
  • Mutating Webhooks nur per Opt-in.
  • Kein Server-Side Diff beim Anlegen neuer Ressourcen.
  • Ein abgelehnter Dry-Run blockiert die Diff-Anzeige der gesamten Application.
  • Mischbetrieb mit Client-Side Apply kann Änderungen verschleiern.
  • Bei der Umstellung bleiben alte managedFields-Einträge von kubectl-client-side-apply bestehen und können Ownership-Konflikte auslösen.
  • Nicht der Default: muss aktiv eingeschaltet werden.
8

Aktivieren und migrieren

Server-Side Diff lässt sich global oder pro Application einschalten. Die Annotation pro Application hat Vorrang und erlaubt auch das gezielte Abschalten.

Global

Im ConfigMap argocd-cmd-params-cm, danach den Application Controller neu starten:

apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  controller.diff.server.side: "true"
# Standardinstallation: der Controller läuft als StatefulSet
kubectl -n argocd rollout restart statefulset argocd-application-controller
Operator-verwaltete Instanzen: Wird Argo CD über einen Operator betrieben, kann dieser direkte Änderungen an der ConfigMap überschreiben. Den passenden Weg über die Operator-CR in dessen Doku prüfen – oder mit der Annotation pro Application arbeiten, die davon unabhängig ist.

Pro Application

Per Annotation, hier zusammen mit Mutating Webhooks und Server-Side Apply:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
  annotations:
    argocd.argoproj.io/compare-options: ServerSideDiff=true,IncludeMutationWebhook=true
spec:
  syncPolicy:
    syncOptions:
      - ServerSideApply=true

Pro Application abschalten, wenn global aktiv:

metadata:
  annotations:
    argocd.argoproj.io/compare-options: ServerSideDiff=false

Vorgehen bei der Migration

  1. Klein anfangenServer-Side Diff zunächst für einige unkritische Applications per Annotation aktivieren.
  2. Diffs vergleichenVor und nach der Umstellung mit argocd app diff <app> gegenüberstellen.
  3. Controller-Felder entfernenFelder, die Controller verwalten (z. B. replicas bei HPA), aus den Manifesten nehmen.
  4. ignoreDifferences abbauenÜberflüssig gewordene Einträge entfernen.
  5. Server-Side Apply zuschaltenFür dieselben Applications die Sync-Option ServerSideApply=true setzen.
  6. Global aktivierenDanach global einschalten und problematische Applications gezielt per Annotation ausnehmen.
